# 엔진 품질 재측정 결과 (PDFium 2.15.1 / MuPDF 1.28.6, Node 24, Windows 11)

작업지시서 '엔진 품질 재측정' 중 미측정 항목. 실행: `node measure2.mjs` (결과물 `out2/`, 항목별 JSON `out2/m*.json`).
판정 기준: 렌더 가시성은 "주석/값 추가 전후 PNG의 해당 영역 화소 차이(>0 이면 무엇이 그려짐)", 저장 검증은 `qpdf --check`, 서명은 pyHanko 검증.
사실은 사실로, 추측은 `(추측)`으로 표시했다. 합성 샘플(작업지시서의 3종 + 이번에 만든 form.pdf/signed.pdf) 기준이며 실제 PDF 샘플은 아니다.

## 1. 한글 폰트 등록 (PDFium, ko_nonembedded.pdf)

| 항목 | PDFium | MuPDF |
|---|---|---|
| 래퍼 노출 여부 | `FPDF_SetSystemFontInfo`, `FPDF_AddInstalledFont`, `FPDF_GetDefaultSystemFontInfo` 모두 `@embedpdf/pdfium` 래퍼에 노출됨 (`index.d.ts:196,210,267`) | 해당 없음 |
| 기준선(폰트 미등록) | 한글 전부 빈칸 (`out/ko_nonembedded.pdfium.png`) | 한글이 그려짐 (`out/ko_nonembedded.mupdf.png`) |
| 맑은 고딕 등록 | **성공**. 한글·특수문자 모두 그려짐 (`out2/m1_ko_nonembedded.pdfium.malgun.png`) | 등록 불필요 |
| Noto Sans KR VF 등록 | **성공** (`out2/m1_ko_nonembedded.pdfium.noto.png`). 가변 폰트 기본 인스턴스라 가는 굵기로 보임 | |

방법(`m1_font.mjs`): `FPDF_SYSFONTINFO` 구조체(36바이트, 콜백 8개)를 WASM 힙에 직접 만들고 `Module.addFunction`으로 콜백을 연결해 `FPDF_SetSystemFontInfo` 호출. `EnumFonts` 콜백 안에서 `FPDF_AddInstalledFont(mapper, "Malgun Gothic", 129)`, `MapFont`는 charset 129(한글)이면 핸들 반환, `GetFontData`는 table=0이면 폰트 전체, 아니면 sfnt 테이블을 잘라서 반환. 막힌 지점은 없었다.
- PDFium이 요청한 폰트: `MapFont w=290 cs=129 face=HYGothic-Medium / HYSMyeongJo-Medium` (Adobe-Korea1 CID 폰트 대체 요청이 charset 129로 들어옴).
- `FPDF_GetDefaultSystemFontInfo`는 값(1787640)을 반환하지만 기본 폰트가 실제로 한글을 제공하는지는 확인하지 않았다(WASM 안에는 파일시스템 폰트가 없음 - 기준선에서 빈칸이므로 사실상 한글 없음).
- 폰트 파일은 JS가 공급해야 한다: 맑은 고딕 13.4MB, Noto Sans KR VF 10.4MB(`C:\Windows\Fonts`). 번들 가능성은 파일 크기와 라이선스 문제가 있다. 맑은 고딕은 Windows 시스템 폰트라 재배포 권리를 확인해야 한다 `(추측: 재배포 불가일 가능성, 라이선스 미확인)`. 시험용 사용일 뿐이다.
- 브라우저에서는 `C:\Windows\Fonts`를 읽을 수 없으므로(추측: Local Font Access API 또는 CDN 다운로드 필요) 실제 앱의 폰트 공급 경로는 별도 설계가 필요하다. 이 항목은 Node에서만 측정했다.

## 2. 주석 저장 (하이라이트 / 사각형 / 메모 / FreeText)

시험: ko_embedded.pdf 1쪽에 5개 주석(Highlight, Square, Text, FreeText 영문, FreeText 한글) 추가 → 저장 → qpdf → 두 엔진으로 재로드해 개수·Subtype·Contents 읽기 → 3개 렌더러(PDFium, MuPDF, pdf.js)로 그려 영역 화소 차이 확인.

| 항목 | PDFium | MuPDF |
|---|---|---|
| 5종 생성 | 모두 성공. FreeText도 `FPDFPage_CreateAnnot(3)` 으로 생성됨 (`EPDFPage_CreateAnnot` 불필요) | 모두 성공 (`createAnnotation`) |
| 저장 후 `qpdf --check` | 통과 | 통과 |
| 재로드 개수 | 자기 파일 5개 / MuPDF가 읽어도 5개 | MuPDF 5개(Popup 제외). **PDFium은 6개로 읽음**: Text 주석 생성 시 MuPDF가 Popup(subtype 16)을 함께 만듦 |
| Subtype/Contents(한글 포함) | 양 엔진에서 전부 정확히 읽힘 | 양 엔진에서 전부 정확히 읽힘 |
| appearance stream | 생성 직후엔 없음(`EPDFAnnot_HasAppearanceStream`=false). 명시적으로 `EPDFAnnot_GenerateAppearance` 호출해야 생김. 호출 후 5종 모두 AP 있음 | `annot.update()` 가 AP 생성. 5종 모두 AP 있음 |
| 렌더 가시성 (본인 파일을 PDFium/MuPDF/pdf.js로) | 5종 모두 세 렌더러에서 그려짐 (한글 FreeText 제외, 아래) | 5종 모두 MuPDF·pdf.js에서 그려짐. PDFium에서는 한글 FreeText만 안 보임 |
| 영문 FreeText | 박스 + 텍스트 그려짐 | 텍스트만(테두리 없음) 그려짐 |
| **한글 FreeText** | **텍스트가 안 그려짐**(박스만). 세 렌더러 모두 동일 (`out2/m2_ko_freetext_check.png`). DA를 `/Helv`로 줬고 AP 글꼴이 Helv 한 개뿐. 시스템 폰트를 등록해도(항목1) 달라지지 않음 | 그려짐(MuPDF, pdf.js). AP가 비내장 Type0 `Batang`(UniKS-UTF16-H)을 씀. **PDFium은 폰트 미등록 시 안 보이고, 맑은 고딕 등록 시 보임** (`out2/m2_annot.kofont.*`) |
| API 제약 | WASM 래퍼에 `EPDFAnnot_*` 확장이 있어 AP 생성·색·테두리·FreeText 가능. 한글 FreeText는 방법을 못 찾음(`DA`에 한글 폰트를 줄 방법 시도 안 함: 미확인) | `setDefaultAppearance`는 폰트 이름 인자만, 내장 폰트 선택에 의존. 한글은 비내장 폰트 참조라 뷰어 폰트에 의존 |

미측정: 다른 뷰어(Acrobat 등)에서 주석을 "다시 편집"할 수 있는지(작업지시서 성공 기준)는 측정하지 않았다. Acrobat은 사용하지 않았다.

## 3. 양식 (reportlab으로 만든 텍스트 필드 2개: name, memo)

값: name=`Hello 123`, memo=`홍길동 한글 값`. 모든 변형이 qpdf 통과, 두 엔진 재로드에서 값 정확히 읽힘.

| 방식 | 값 쓰기·재로드 | 위젯 AP | 영문 가시성 | 한글 가시성 (폰트 미등록 PDFium) | 한글 (맑은 고딕 등록 PDFium) |
|---|---|---|---|---|---|
| PDFium `EPDFAnnot_SetFormFieldValue` + `EPDFAnnot_GenerateFormFieldAP` | 성공 | 있음 | 모든 렌더러 | **안 보임**(PDFium, MuPDF, pdf.js 모두) | 여전히 안 보임 |
| PDFium `FPDFAnnot_SetStringValue("V")` + GenerateFormFieldAP | 성공 | 있음 | 모든 렌더러 | 안 보임(위와 같음) | 안 보임 |
| PDFium `FORM_SetFocusedAnnot`+`FORM_SelectAllText`+`FORM_ReplaceSelection` (폼 입력 시뮬레이션) | 성공 | 있음 | 모든 렌더러 | PDFium 안 보임 / MuPDF 보임 / pdf.js 두부(□) 문자 | **PDFium 보임**, MuPDF 보임, pdf.js는 여전히 두부 문자 |
| MuPDF `widget.setTextValue` | 성공 | 있음 | 모든 렌더러 | PDFium 안 보임 / MuPDF·pdf.js 보임 | PDFium 보임 |

- PDFium 렌더 API 주의: `FPDF_RenderPageBitmap` 만으로는 위젯(양식 필드)이 전혀 그려지지 않고, `FPDF_FFLDraw`(+ `PDFiumExt_InitFormFillEnvironment`)를 호출해야 그려진다(기준선과 값 입력본 모두 `pdfium` 렌더러 영역 차이 0, `pdfium_ffl`에서만 차이).
- MuPDF가 PDFium 저장본의 한글 값을 그려 주는 이유는 확인하지 않았다 `(추측: MuPDF가 로드 시 AP를 자기 폰트로 다시 만들 수 있음)`.
- 결론 수치는 `out2/m3_forms.json`, `m3_forms.kofont.json`.

## 4. 증분 저장·서명 (pyHanko로 서명한 form.pdf, 자체 서명 인증서)

서명 PDF는 만들 수 있었다(reportlab 양식 PDF + pyHanko 서명 필드 `Sig1` + openssl 자체 서명 pkcs12, `make_fixtures2.py`). 원본 12074바이트, ByteRange `[0,7108,11498,576]`. 인증서가 자체 서명이라 `trusted`는 항상 false이며 이는 측정 대상이 아니다.
"intact"는 pyHanko가 ByteRange 구간의 해시를 다시 계산해 일치하는지(= 서명 무결성), "수정 수준"은 pyHanko가 서명 이후 변경 내용을 분석한 결과다.

| 케이스 | 원본 접두 보존 | ByteRange·서명 intact | pyHanko 수정 수준 | qpdf | 크기 |
|---|---|---|---|---|---|
| PDFium 증분(flag 1), 주석 추가 | 예 | 예 (ByteRange 동일) | OTHER | 통과 | 16069 |
| PDFium 증분, 필드 채움(FORM_ReplaceSelection) | 예 | 예 | OTHER | 통과 | 17246 |
| PDFium 증분, **편집 없음** | 예 | 예 | **OTHER** (편집이 없는데도 객체를 다시 씀, 폼 환경 없이도 동일: 14080바이트) | 통과 | 15547 |
| PDFium 전체 저장(flag 0) | **아니오** | **아니오** (intact=false) | - | 통과 | 10478 |
| MuPDF 증분(`incremental=yes`), 주석 추가 | 예 | 예 | OTHER | 통과 | 13030 |
| MuPDF 증분, 필드 채움 | 예 | 예 | **FORM_FILLING** (허용 범위 내 변경으로 분류) | 통과 | 12957 |
| MuPDF 증분, **편집 없음** | 예 | 예 | **NONE** (원본과 바이트 동일, 12074) | 통과 | 12074 |
| MuPDF 전체 저장(옵션 없음) | **아니오** | **아니오** (intact=false) | - | 통과 | 10948 |

- 두 엔진 모두 증분 저장은 원본 바이트를 접두로 보존하고 서명 ByteRange 해시 무결성(intact)을 유지한다. 전체 저장은 두 엔진 모두 서명을 깨뜨린다(서명 UI에서 증분만 쓰도록 강제해야 함).
- 차이: MuPDF는 필드 채움을 "양식 입력"(서명을 무효로 하지 않는 변경)으로 분류되게 쓰고, 편집이 없으면 아무것도 쓰지 않는다. PDFium은 편집 유무와 상관없이 기존 객체(페이지, 위젯, AcroForm 등)를 다시 써서 pyHanko가 모두 OTHER로 분류한다. OTHER가 Acrobat에서 "서명 이후 변경됨" 경고를 일으키는지는 확인하지 못했다 `(추측: 일으킬 가능성)`.
- 주석 추가는 MuPDF도 OTHER로 분류됨. 서명 PDF에 주석을 달 때 두 엔진 모두 이 분류를 피하지 못했다.
- PDFium은 `FPDF_GetSignatureCount`, `FPDFSignatureObj_GetByteRange`로 서명 정보를 읽을 수 있다(전 케이스에서 1개, 동일 ByteRange 확인). MuPDF JS API(`mupdf.d.ts`)에는 서명 생성/검증 메서드가 노출되지 않음(`canBeSavedIncrementally`, `validateChangeHistory` 만 있음, 호출해 보지는 않음). 서명 검증은 이번 측정에서 pyHanko가 맡았다. 서명 생성은 두 엔진 모두 하지 않았다.
- 미측정: Acrobat 등 실제 뷰어의 서명 상태 표시, DocMDP 인증 서명, 다중 서명.

## 5. MuPDF 저장 garbage (scan.pdf)

scan.pdf는 실제로 2쪽이다(작업지시서 설명의 6쪽이 아님). 마지막 쪽 1개를 삭제하고 저장.

| 저장 방식 | 크기(바이트) | 객체 수(qpdf) | 쪽 수 | qpdf |
|---|---|---|---|---|
| 원본 | 1,136,605 | 9 | 2 | |
| MuPDF 삭제 후 옵션 없음 | 1,136,545 | 9 | 1 | 통과 (삭제 쪽 이미지가 그대로 남음) |
| MuPDF `garbage=compact` | **555,576** | 6 | 1 | 통과 |
| MuPDF `garbage=deduplicate` | 555,576 | 6 | 1 | 통과 |
| MuPDF `garbage=compact,compress` | 555,590 | 6 | 1 | 통과 |
| MuPDF `garbage=deduplicate,compress,clean` | 555,588 | 6 | 1 | 통과 |
| MuPDF `incremental=yes` | 1,136,795 | 9 | 1 | 통과 (삭제 쪽 객체가 남음) |
| PDFium `FPDF_SaveAsCopy(0)` | 555,668 | 6 | 1 | 통과 (garbage 옵션 없이도 자동 정리) |

- MuPDF는 `garbage=compact` 이상을 줘야 삭제 쪽의 이미지 객체가 정리되고, 그 결과가 PDFium 기본 저장과 거의 같은 크기가 된다. 옵션 이름은 `garbage=compact|deduplicate`이며 `garbage=yes`는 이 버전에서 "unknown garbage option" 오류를 낸다.
- 2쪽 파일에서 마지막 쪽을 5회 삭제하려는 시험(범위 초과)에서 MuPDF는 `malformed page tree` 오류를 던졌고(정확한 발생 시점 미확인), PDFium은 0쪽 파일을 저장했다(qpdf exit 2). 이 시험의 산출물은 정리했다.
- 이 객체 수 9→6은 이미지 객체가 쪽 단위로 정리되는 작은 파일이다. 본문 텍스트가 많은 대형 PDF의 정리 효과는 측정하지 않았다.

## 6. MuPDF WASM 바이트 외부 주입

소스 근거: `node_modules/mupdf/dist/mupdf.js:27` 에서 `await libmupdf_wasm(globalThis["$libmupdf_wasm_Module"])` 를 호출한다. 즉 모듈 로드 전에 전역 `$libmupdf_wasm_Module` 객체를 설정하면 Emscripten Module 옵션으로 전달된다. `mupdf-wasm.js` 는 `wasmBinary`, `instantiateWasm`, `locateFile`을 처리한다.

- 방법 A (확인됨): `globalThis.$libmupdf_wasm_Module = { wasmBinary: Uint8Array }` 설정 후 `await import('mupdf')`. 파일 경로가 존재하지 않는 `locateFile`을 줘도 문서가 열리고 2쪽을 읽었다 → 외부 바이트로 초기화됨 (`m6_mupdf_wasm.mjs`). `locateFile`은 경로 문자열 계산용으로 호출될 뿐 해당 파일을 읽지 않는다.
- 방법 B (확인됨): `instantiateWasm(imports, done)` 훅으로 `WebAssembly.instantiate`를 직접 수행. 호출 1회, 문서 열림 (`m6b_instantiate.mjs`).
- 주의: `mupdf.js` 는 최상위 await로 즉시 초기화하므로 정적 `import`보다 먼저 전역을 설정해야 한다. 단일 HTML 번들에서는 WASM을 base64로 인라인한 뒤 전역을 설정하고 동적 `import()`(또는 번들러에서 평가 순서 보장)를 써야 한다. 이는 Node에서만 확인했고 브라우저 번들/`file://` 환경은 확인하지 않았다.
- 크기: `mupdf-wasm.wasm` 10.4MB(brotli 3.6MB), PDFium WASM은 `index.js` 래퍼와 별도로 제공됨(크기 비교는 이번 범위 밖).

## 7. 브라우저 PDF.js 한글 미내장 렌더링

가능했다. playwright-core(브라우저 다운로드 없이) + 설치된 Chrome 157(`C:\Program Files\Google\Chrome`) headless로 로컬 HTTP 서버에서 pdfjs-dist 6.5.438을 로드해 ko_nonembedded.pdf를 캔버스에 그림(`m7_browser.mjs`).
- 결과: **한글이 정상 표시됨** (`out2/m7_ko_nonembedded.chrome_pdfjs.png`), 임베디드 샘플도 렌더됨. 서체는 명조/바탕 계열 대체 글꼴.
- 한계: 이 PC에 한글 시스템 폰트(맑은 고딕, 바탕 등)가 설치돼 있어 브라우저가 대체 글꼴을 찾은 것이다. 한글 폰트가 없는 PC(예: 한글 폰트 미설치 Linux/macOS 환경)에서의 결과는 측정하지 못했다. 콘솔 오류는 404 하나(리소스 하나, 원인 미확인 `(추측: favicon)`)이며 렌더에는 영향 없었다.

## 기본 엔진 결정에 영향을 주는 판단 요약

| 관점 | 앞선 쪽 | 차이의 성격 |
|---|---|---|
| 한글 미내장 렌더링(폰트 공급 부담) | **MuPDF** | 뚜렷함. MuPDF는 폰트 없이 그려짐. PDFium은 폰트(10MB급) 공급 + 콜백 구현이 필요하나, 등록하면 같은 품질로 그려짐(해결 가능한 차이) |
| 한글 주석(FreeText) | **MuPDF** | 뚜렷함. PDFium은 FreeText 한글을 못 그림(박스만). 폰트 등록과 무관. 한글 메모(Text)·Contents 저장은 양쪽 모두 정상 |
| 영문/일반 주석(하이라이트·사각형·메모·FreeText 영문) | 동등 | 양쪽 모두 생성·qpdf 통과·재로드·3종 렌더에서 보임. PDFium은 `EPDFAnnot_GenerateAppearance`를 직접 호출해야 하는 점만 다름 |
| 양식 한글 값 | **MuPDF** | 뚜렷함. MuPDF 저장본은 PDFium(폰트 등록 시)·MuPDF·pdf.js 모두 한글이 보임. PDFium 저장본은 pdf.js에서 두부 문자 또는 안 보임이 나오는 경우가 있음 |
| 양식 영문 값 | 동등 | 양쪽 정상. 단 PDFium은 렌더에 `FPDF_FFLDraw` 폼 환경이 필요 |
| 증분 저장·서명 보존 | 약간 **MuPDF** | 애매함. 둘 다 접두 보존·ByteRange 무결성 유지. MuPDF는 편집이 없으면 무변경, 필드 채움을 허용 변경으로 분류. PDFium은 항상 OTHER. 이것이 실제 뷰어에서 의미 있는 차이인지는 확인 못함 |
| 삭제 쪽 객체 정리 | 동등 | 애매함. PDFium은 기본 저장이 정리, MuPDF는 `garbage=compact`를 줘야 같은 결과 |
| WASM 초기화 제어 | 동등 | MuPDF도 외부 바이트 주입 가능(전역 설정 순서 주의). PDFium은 기존 하네스에서 `wasmBinary` 주입으로 동작 |

종합(사실에 근거한 판단): 한글 렌더링·한글 주석/양식에서는 MuPDF가 뚜렷하게 유리하고, 영문 주석·삭제 쪽 정리는 차이가 없으며, 증분 저장은 MuPDF가 약간 유리하나 애매하다. PDFium을 기본으로 하려면 한글 폰트 번들 + 시스템 폰트 훅 + 한글 FreeText 해결이 필요하다(해결 방법 미확인). 라이선스 부담(MuPDF AGPL-3.0-or-later, `mupdf/package.json`)은 이번 측정 범위 밖이며 결정 시 별도 고려해야 한다. 렌더링 성능·메모리·번들 크기는 이번에 다시 측정하지 않았다.
