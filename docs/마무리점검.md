# 마무리 점검

## 요약

작업지시서의 성공 기준 3개, 작업별 완료 기준 10개, 미정 사항 6개, 유의할 위험 5개를 점검했다.
24개 항목 중 13개는 확인했고, 10개는 일부만 확인했고, 1개는 확인하지 못했다.
일부만 확인한 항목은 대부분 Acrobat 같은 외부 뷰어를 쓰지 못했다는 한 가지 이유로 남았다.
확인하지 못한 세부 사항은 12개이고, 직접 확인하는 방법을 아래에 적었다.
기본 엔진은 MuPDF로 정했고 근거는 `docs/엔진결정.md`에 있다.
사용자가 정해야 할 사항은 마지막에 모았다. 인쇄와 UI 개편 뒤의 변경은 `이후 변경과 재검증`에 따로 적었다.

## 배경

### 증거의 출처

- 직접 실행: 2026-11-13에 `app` 폴더에서 `node --test test/*.test.mjs`(132개 통과, 실패 0)와 `npm run check`(146개 파일, 오류 0, 경고 0)를 돌렸다.
- 화면 시험(2026-11-13 이전): Chrome을 원격 제어해서 `dist-static`(로컬 HTTP 서버)과 `dist-single/index.html`(`file://`)을 각각 시험했다. 로그와 스크린샷은 임시 작업 폴더에 있었고 저장소에는 들어 있지 않다. 이 시험은 아래 `이후 변경과 재검증`의 Playwright e2e로 옮겨져 저장소에 남았다.
- 엔진 측정: `harness/결과.md`와 `harness/out2/`의 JSON, PNG, PDF를 근거로 했다. Node 환경의 합성 샘플 기준이다.

이 표에서 `로그`는 위 폴더의 `reg-*-single.log`(single 빌드)와 `reg-*-static.log`(static 빌드)를 뜻한다.

### 미결

- single 빌드의 쪽 조작 시험에서 남은 데이터 정리 2건이 실패했던 원인은 시험 스크립트였다. 시나리오들이 Chrome 프로필을 공유해서 앞 시나리오의 저장 옵션이 다음 시나리오로 새는 경우가 있었다. 실패 수치(증분 1,897바이트, 정리 후 2,097바이트)가 이 경로와 일치한다. 시나리오마다 새 프로필을 쓰도록 고쳤고, static과 single 모두 97건이 통과했다. 앱 코드는 고치지 않았다. 고친 뒤의 전체 실행은 빌드마다 1회뿐이다.
- single 빌드의 정리 모드 설정 복원 2건 실패는 수정 전 시험 스크립트의 로그였다(`org-single.log`). 현재 스크립트로는 단독 5회가 모두 통과했고 전체 176건도 통과했다. 설정 저장·복원 단위 시험 4건을 추가했다(`app/test/settings.test.mjs`).

## 이후 변경과 재검증

위 점검은 인쇄와 UI 개편 전의 상태를 기준으로 했다.
그 뒤에 다음을 바꿨고, 아래 시험을 모두 다시 돌렸다.

- 인쇄 기능, 확대 슬라이더와 선택 상자, 보기 모드 Ctrl+휠 확대, 쪽 드래그 고스트, 정리 모드 썸네일 최대 640px
- 디자인 토큰 정리와 모션 전반(스프링 기반, 동작 줄이기 대응)
- 코드 점검에서 나온 결함 수정: 엔진 계층(캐시된 WASM 해시 재검증, PDFium 라디오 계약, PDFium 암호 PDF 저장, 워커 오류 처리, MuPDF 자원 해제, 렌더 크기 상한), 상태 계층(저장 뒤 렌더 대기열 유실, 되돌리기 실패 경로, 엔진 수명 경쟁, 메모리 상한), 화면 계층(드래그 중 단축키로 엉뚱한 쪽이 이동, 팝오버 포커스 복귀, 인쇄 취소)

| 시험 | 결과 |
|---|---|
| `node --test test/*.test.mjs` | 219개 통과, 실패 0 |
| `npm run check`, `npm run check:e2e` | 오류 0 |
| `npm run build` | static, single 모두 성공 |
| `npm run e2e`(Playwright, static + single) | 292개 통과, 실패 0, 건너뜀 10(빌드 종류별로 해당 없는 시험) |

e2e는 열기, 보기, 쪽 조작, 저장, 다중 탭, 정리 모드, 주석, 양식, 설정, 접근성, 인쇄, 확대, 드래그 고스트, 모션을 두 빌드에서 시험한다.
저장본은 `qpdf --check`와 재로드로 검증한다.
이 시험이 위 `증거의 출처`의 원격 제어 시험을 대신한다.
라이트와 다크 화면은 직접 열어 확인했다.

다음은 확인하지 못했다.

| 항목 | 이유 | 직접 확인하는 방법 |
|---|---|---|
| 실제 인쇄 창과 프린터 출력 | 헤드리스에서는 인쇄 창이 뜨지 않는다. `window.print`를 대역으로 바꾸고 `page.pdf()`로 인쇄 미디어 결과를 검증했다 | 일반 Chrome에서 `dist-static`을 http로 열어 인쇄 미리보기가 뜨는지, 첫 쪽이 비지 않는지(코드는 PDF를 올린 뒤 0.4초 기다린다), 가로·세로 섞인 문서의 방향과 여백이 맞는지 본다 |
| 인쇄 미리보기를 취소하거나 인쇄한 뒤의 정리 | `afterprint`를 시험에서 직접 발생시켰다 | 인쇄 미리보기를 닫은 뒤 화면에 남은 요소가 없는지 본다. 신호가 끝내 없으면 10분 뒤 정리된다 |
| 300쪽을 이미지 방식으로 인쇄할 때의 메모리 | 300쪽 준비 중 브라우저 전체 메모리가 최대 1.4GB까지 올랐다(자동 방식은 이 방식을 쓰지 않는다). 실제 인쇄 미리보기에서는 재지 못했다 | 300쪽 문서를 이미지 방식으로 인쇄해 작업 관리자에서 메모리를 본다 |
| 실제 GPU에서의 모션 프레임률 | 시험은 소프트웨어 렌더링 헤드리스 Chrome에서 했다. 드래그 고스트와 재정렬 연출은 이 환경에서 프레임 일부가 33ms를 넘었다 | 일반 Chrome에서 300쪽 문서로 드래그와 재정렬을 해 보고, 끊기면 개발자 도구 성능 탭으로 잰다 |
| Firefox와 Safari | Chrome만 시험했다. 모션에 `linear()` 이징과 `:has()`를 쓴다 | 두 브라우저에서 열어 화면과 인쇄 방식 판정이 같은지 본다 |
| 터치 기기에서 길게 눌러 연 메뉴의 포커스 | 마우스·키보드 경로와 터치 에뮬레이션만 시험했다 | 실제 터치 기기에서 쪽을 길게 눌러 메뉴를 열고 `Esc`나 바깥 탭으로 닫아 본다 |
| 정리 모드에서 브라우저 메뉴로 직접 인쇄 | 격자는 일부 칸만 그려지고 저해상도라, 인쇄 직전에 모두 그릴 수 없다. 억지로 하면 일부 쪽만 조용히 인쇄된다 | 앱의 인쇄 창(`Ctrl` `P`)을 쓴다. 필요하면 인쇄 직전에 보기 모드로 바꾸는 설계를 따로 정한다 |

## 직접 확인하는 방법

### 확인하지 못한 항목

| 항목 | 확인하지 못한 이유 | 직접 확인하는 방법 |
|---|---|---|
| Acrobat에서 저장본이 깨지지 않고 열리는지 | Acrobat을 쓰지 않았다 | 쪽 조작, 주석, 양식 저장본(`ops-saved-single.pdf`, `ann-single-shapes.pdf`, `ann-single-form-all.pdf`)을 Acrobat으로 열어 쪽 수, 회전, 주석 모양을 비교한다 |
| 다른 뷰어에서 주석을 다시 편집하는 시험 | 외부 뷰어로 편집하지 않았다 | `ann-single-shapes.pdf`를 Acrobat에서 열어 사각형을 끌고, 메모 내용을 고치고, 텍스트 상자의 글자를 바꿔 본다. 하이라이트도 선택되는지 확인한다 |
| 서명 PDF를 증분 저장한 뒤 Acrobat의 서명 유효성 | 서명 검증을 pyHanko로만 했다. 자체 서명 인증서라 신뢰 여부는 시험 대상이 아니다 | `harness/out2/fixtures/signed.pdf`를 앱에서 회전 후 저장하고, Acrobat의 서명 패널에서 `서명 이후 변경됨` 경고 여부를 본다. 주석을 추가한 저장본도 같은 방법으로 본다. 두 엔진 모두 pyHanko가 `ILLEGAL_MODIFICATIONS`로 분류했으므로 이 경우를 꼭 본다 |
| 네트워크를 끊은 상태의 두 번째 실행 | 같은 프로필로 다시 여는 것까지만 했다 | single 빌드로 엔진을 한 번 내려받은 뒤, 개발자 도구의 네트워크 탭에서 오프라인으로 바꾸고 같은 브라우저에서 PDF를 연다 |
| 탐색기 더블클릭으로 단일 HTML을 여는 시험 | 원격 제어 브라우저에서 `file://` 주소로 열었다 | 탐색기에서 `dist-single/index.html`을 더블클릭해 기본 브라우저로 열고, PDF를 끌어다 놓아 첫 실행 안내와 설정 저장이 동작하는지 본다 |
| 보기 모드 300쪽 본문 스크롤의 프레임 수치 | 정리 모드 격자 수치만 로그로 남았다 | `harness/samples`의 PDF를 여러 번 병합해 300쪽 문서를 만들고 보기 모드에서 스크롤하며 개발자 도구의 성능 탭으로 프레임 간격을 잰다 |
| 실제 PDF(한글 문서, 폰트 미내장, 스캔본, 암호 PDF, 대용량) | 받은 샘플이 없다. 암호 PDF를 열었을 때의 안내 화면은 시험하지 않았다 | 가진 PDF를 열어 쪽 그림, 저장, 다시 열기를 확인한다. 암호 PDF는 열 수 없다는 안내가 나오는지 본다 |
| 한글 폰트가 없는 PC의 PDF.js 렌더링 | 이 PC에 한글 시스템 폰트가 있다 | 한글 폰트가 없는 환경에서 `harness/m7_browser.mjs`를 실행하거나 PDF.js 뷰어로 `ko_nonembedded.pdf`를 연다 |
| Ctrl+Tab과 Ctrl+W를 브라우저가 가로채는지 | 원격 제어 브라우저는 키 이벤트를 직접 보내 브라우저 단축키를 거치지 않는다 | 일반 Chrome 창에서 PDF를 두 개 열고 두 키를 눌러 앱의 탭이 바뀌는지, 브라우저 탭이 바뀌거나 닫히는지 본다 |
| 맑은 고딕 재배포 라이선스 | 라이선스 문구를 확인하지 않았다 | Windows 글꼴 라이선스 문서를 확인하거나, 번들 대상을 라이선스가 명확한 글꼴(Noto Sans KR 등)로 바꾼다 |
| single 빌드의 남은 데이터 정리 시험이 다시 실패하는 경우 | 원인은 시험 프로필 공유로 판단했지만, 실패 실행의 설정 상태를 직접 관측하지는 못했다 | 정리 시나리오 첫머리에서 `localStorage`의 `pdf-edit:settings`를 로그로 남긴다. 증분 꺼짐·정리 켜짐이면 누수가 재발한 것이다 |
| `file://`에서 브라우저를 껐다 켠 뒤 설정이 남는지 | 시험 환경의 Chrome은 프로세스를 다시 띄우면 `file://`의 localStorage가 남지 않았다. 일반 설치 Chrome에서의 동작은 보지 못했다 | 단일 HTML을 더블클릭해 열고 정리 모드로 바꾼 뒤 브라우저를 완전히 닫았다 다시 열어 모드가 유지되는지 본다 |

## 사용자에게 남은 결정

| 주제 | 현재 동작 | 정할 것 |
|---|---|---|
| 도구 전환 | 하이라이트는 만든 뒤에도 계속 켜져 있다. 사각형·원·메모·텍스트 상자·이미지는 하나 만들면 선택 도구로 돌아가고 방금 만든 주석이 선택된다 | 이 구분을 유지할지 정한다 |
| 빈 메모와 빈 텍스트 상자 | 내용이 비어 있으면 아무 안내 없이 취소된다 | 안내를 둘지, 빈 주석을 만들지 정한다 |
| 글자가 있는 쪽의 빈 곳 끌기 | 하이라이트가 만들어지지 않는다. 글자가 없는 쪽(스캔본)에서는 영역 하이라이트가 만들어진다 | 글자가 있는 쪽에서도 영역 하이라이트를 만들지, 안내를 띄울지 정한다 |
| 서명 이미지 단축키 | `S`가 이미지 선택 창을 연다 | `S`를 유지할지, 다른 키로 바꿀지 정한다 |
| 선 도구 | 없다. MuPDF 어댑터는 하이라이트·사각형·원·메모·텍스트 상자·이미지만 새로 만들고 선과 펜은 만들지 못한다(`mupdf-adapter.ts`의 `addAnnotation`). 이미 있는 선·펜 주석은 읽고 옮기고 고칠 수 있다 | 선 도구를 만들지 정한다. 만든다면 MuPDF 어댑터에 선 주석 추가를 구현해야 하고, 이는 시도하지 않았다 |
| Ctrl+Tab과 Ctrl+W | 앱이 직접 처리한다(`App.svelte`). 브라우저가 먼저 처리하는지는 확인하지 못했다 | 일반 브라우저에서 확인한 뒤, 가로채이면 대체 키를 정한다 |
| 정리 모드의 화면 구성 | 아래 다섯 가지가 열려 있다 | 항목별로 정한다 |
| 정리 모드: 선택한 쪽 모두를 새 파일로 | 파일 목록 쪽의 기능으로 있다 | 툴바에도 같은 버튼을 둘지 정한다 |
| 정리 모드: 툴바의 파일 열기 아이콘 | 정리 모드에서는 숨겨진다 | 계속 숨길지 정한다 |
| 정리 모드: 작은 칸의 호버 아이콘 | 칸 폭이 112px 미만이면 회전·복제·삭제 아이콘이 숨겨진다(`PageGrid.svelte`, `Thumbnails.svelte`) | 기준을 바꿀지 정한다 |
| 정리 모드: 보기 패널 폭 100px | 에이전트 보고에 따르면 썸네일이 44px가 된다. 이 점검에서 직접 재지는 않았다 | 최소 폭을 올릴지 정한다 |
| 정리 모드: 분할 팝오버 | 선택한 범위를 미리 채우지 않는다 | 미리 채울지 정한다 |
| 설정의 확대 배율 | 기본값과 마지막 값이 하나로 합쳐져 있다. 마지막으로 쓴 배율이 다음 실행의 시작 배율이다(`settings.ts`) | 기본 배율을 따로 둘지 정한다 |
| 한글 폰트 번들 | PDFium용 한글 폰트를 번들하지 않았다. MuPDF가 기본이라 현재 쓰이지 않는다 | PDFium을 쓸 일이 있다면 10~13MB 폰트를 내려받게 할지 정한다 |
| 맑은 고딕 재배포 | 코드에 번들되어 있지 않다. 시험은 이 PC의 `C:/Windows/Fonts/malgun.ttf`를 읽는다 | 재배포 라이선스를 확인할지, 다른 폰트를 쓸지 정한다 |
| 서명된 PDF의 편집 | 증분 저장은 서명 값을 깨뜨리지 않지만, 주석 추가나 회전은 `서명 이후 변경`으로 분류된다 | 서명된 문서를 열었을 때 이 점을 미리 알리는 안내를 둘지 정한다 |
| 인쇄: 단일 HTML | `file://`에서는 브라우저가 인쇄용 PDF 창 접근을 막아 항상 이미지 방식이다. 이미지 방식은 150~300dpi라 작은 글자가 거칠 수 있다 | 글자가 선명한 인쇄가 필요하면 로컬 http 서버로 연다. 이대로 둘지 정한다 |
| 인쇄: 이미지 압축 | JPEG 품질 0.92로 고정했다. PNG는 선명하지만 메모리가 몇 배 든다 | PNG 선택지를 둘지 정한다 |
| 인쇄: 정리 모드의 선택한 쪽 | 모든 파일의 선택을 합쳐 인쇄한다. 쪽 도구의 `N쪽 선택` 표시는 활성 파일만 센다 | 활성 파일만 인쇄할지 정한다 |
| 인쇄: 범위 입력 순서 | `5,1-3`도 1,2,3,5 순서로 인쇄한다 | 입력한 순서대로 인쇄할지 정한다 |
| 인쇄: 설정 저장 | 방식과 dpi를 마지막 값으로 저장한다 | 저장하지 않을지 정한다 |
| 새 파일 탭의 되돌리기 | 복사·병합으로 만든 탭은 되돌리기를 끝까지 눌러도 닫히지 않고 직접 닫아야 한다. 닫아도 되살릴 곳이 없어 내용을 잃기 때문이다 | 되살리기 수단이나 닫기 확인을 둘지 정한다 |
| 접근성 구조 | 파일 목록(`listbox`)과 쪽 칸(`option`) 안에 버튼이 들어 있어 보조 기술에 완전히 전달되지 않을 수 있다. 바꾸면 e2e 선택자가 크게 바뀐다 | 구조를 바꿀지 정한다 |
